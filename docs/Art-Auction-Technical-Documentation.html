Art Auction Gallery Demo — Technical Documentation

Project: Momas High Society Art Auction (artauctiondemo)
Generated for: Word import — open this file in Microsoft Word, then File → Save As → Word Document (*.docx).

1. Use case

  • Gallery / saleroom demo: Artists upload works (max 10 each); admins schedule timed auctions with opening bids; buyers pre-register with a budget cap, then bid while the auction is live; when the end time passes, the server finalizes sales (highest bid per lot wins).
  • Virtual economy: Buyers start with a self-chosen virtual balance at registration; settlement debits buyers and credits artists.
  • Roles: Artist, Buyer, Admin — no email verification in this demo.
  • Future payments: Registration captures optional Stripe intent (checkbox + notes only; no Stripe API calls).

3. Architecture

3.1 Logical layers

  • Presentation (browser): SPA on Vite dev server (port 5173); production build is static assets in client/dist.
  • API: Express REST on 127.0.0.1:4000 (configurable PORT, HOST).
  • Domain logic: Auction lifecycle (scheduled → live → ended), bid validation, finalize → art_sales.
  • Persistence: SQLite tables for users, arts, auctions, lots, registrations, bids, sales.

3.2 Request flow (typical)

Browser → Vite proxy (/api, /uploads) → Express → middleware (refreshAllAuctions) → route handler → better-sqlite3 → JSON response.

3.3 Key server behaviors

  • refreshAllAuctions: On most requests, updates auction status from wall-clock time; calls finalizeAuction when end time has passed and not yet finalized.
  • finalizeAuction: Transaction: for each lot, insert art_sales if there is a high bid, else return art to available; mark auction finalized.

This stack uses plain objects and JSON, not Java POJOs. Below: logical “entities” and important fields (as returned by API or stored in DB).

8. Database tables and columns

TableColumns
usersid PK AI, name, email UNIQUE, password_hash, role CHECK(artist|buyer|admin), virtual_balance REAL DEFAULT 10000, use_stripe_future INT DEFAULT 0, stripe_placeholder, created_at
artsid PK AI, artist_id FK→users, title, description, image_path, status CHECK(available|in_auction|sold) DEFAULT available, created_at
auctionsid PK AI, name, description, start_at, end_at, status CHECK(scheduled|live|ended), finalized INT DEFAULT 0, created_by FK→users, created_at
auction_artsid PK AI, auction_id FK→auctions ON DELETE CASCADE, art_id FK→arts, starting_bid REAL DEFAULT 0, max_bid_allowed REAL NOT NULL
auction_registrationsid PK AI, auction_id FK CASCADE, user_id FK→users, budget_cap REAL NOT NULL, UNIQUE(auction_id, user_id)
bidsid PK AI, auction_id FK CASCADE, art_id, user_id FK→users, amount REAL, created_at
art_salesid PK AI, auction_id FK→auctions, art_id FK UNIQUE→arts, buyer_id FK→users, final_price REAL, created_at

Indexes: idx_bids_lot (auction_id, art_id); idx_arts_artist (artist_id); idx_auctions_times (start_at, end_at)

9. Additional topics (recommended)

9.1 Security notes (demo level)

  • Change JWT_SECRET via environment for any shared deployment.
  • No rate limiting, CSRF protection, or HTTPS enforcement in this demo.
  • File uploads: type/size limited by Multer; no virus scanning.

9.2 Configuration

9.3 Run commands

  • Both services: repo root npm install then npm run dev
  • API only: cd server && npm run dev
  • Client only: cd client && npm run dev
  • Reset DB: cd server && npm run reset-db

9.4 Known limitations / future work

  • Real-time bids via polling only (no WebSocket).
  • Stripe: UI placeholder only.
  • Single SQLite file — not horizontally scaled.
  • No audit log or admin “undo” for finalized auctions.
